## Reconciliation rules after owner evidence arrives

Normalize identifiers without discarding source path. Compare each owner record to exact repository IDs, names and checksums where supported. Assign one state per file:

- **Confirmed applied** — authoritative ledger record matches the exact source migration identity/checksum and owner confirms the ledger's scope.
- **Confirmed unapplied** — authoritative complete ledger omits it and the owner confirms no alternate runner applied it.
- **Unknown** — missing/partial/untrusted ledger, checksum unavailable or mismatched, multiple runners, or identity uncertainty.
- **Potential conflict** — ID/name collision, checksum mismatch, record with no repository file, duplicate/version ambiguity, failure marker, ordering anomaly, or overlapping DDL/backfill requiring object-level review.

Classify discrepancies separately:

- **Repository file without ledger row:** ledger gap only if the ledger is proven complete; otherwise unknown.
- **Ledger row without repository file:** missing source artifact until recovered/attested; do not recreate from a guessed name.
- **Duplicate ID rows or mismatched checksum:** hold for owner/DBA review; do not pick one.
- **Ledger success but schema mismatch:** migration/schema reconciliation conflict; a ledger record does not prove current object shape.
- **Migration failure/incomplete row:** unknown outcome until the owner verifies transaction and follow-up behavior.
